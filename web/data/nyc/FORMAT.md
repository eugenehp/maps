# City building tiles (`SFT5` / `SFT6`)

Generated by `pipeline <city> tiles`; checked by `pipeline <city> verify`.
Output directory: `web/data/<city>/` — `index.json`, `r<rx>_<rz>_<k>.bin` packs,
`attrs/r<rx>_<rz>.json`, this file.

## Coordinates

- Local metre frame: equirectangular around `index.json` `origin` (lon/lat), WGS84
  metres-per-degree at that latitude. (`bay` shares SF's origin; its x scale is off by up to
  about ±1.5% at the far north/south edges.)
- **x = metres east, z = metres SOUTH.** In three.js (Y up) buildings stand on the XZ plane,
  north is -Z, height goes along +Y. Geographic north-up maps need `north = -z`.
- Tile vertices are `Int16` **decimetres** relative to the tile origin (`f32` metres, the tile
  centre): `x = originX + xz[2k] / 10`, `z = originZ + xz[2k+1] / 10`.
- Tiles are `tileSize` squares; a building belongs to the tile containing its footprint
  centroid (so it may stick out of the square; `bbox` covers it).
- Vertical: a part spans `y = base .. base + height` (metres). `base` is ground elevation above
  the city datum (`index.json` `groundDatum`; SF: NAVD88 metres from LiDAR `gnd_min_m`), or 0
  where the city has no ground data.

## Rings

- Each building has one or more parts (polygons); each part has one outer ring followed by
  zero or more holes.
- No duplicate closing vertex, no consecutive duplicate vertices, at least 3 vertices.
- Orientation, measured with the shoelace sum `S = Σ (x_i·z_{i+1} − x_{i+1}·z_i)` on the stored
  (x, z) values: **outer rings S > 0, holes S < 0**. That is counter-clockwise on paper with
  x right / z up; because z points south it is *clockwise* seen from above with north up
  (i.e. clockwise in lon/lat). Wall normals: for edge a→b with d = b − a, the outward normal
  (outer rings and holes alike) is `(dz, 0, -dx)` in world x/y/z, normalised.

## Tile binary (little-endian): SFT5

The tile layout is implemented once, in the `tilefmt` crate, used by both the pipeline and the
API. The browser's `web/worker.js` has its own reader. Every array is **zero-padded to a
multiple of 4 bytes**.

Header, 32 bytes:

| type | field |
|------|-------|
| u8[4] | magic `"SFT5"` |
| u32 | nB  buildings |
| u32 | nP  parts |
| u32 | nR  rings |
| u32 | nV  vertices |
| u32 | gid0: building b of the tile has gid `gid0 + b` (index.json `tiles[].gid0`) |
| f32 | originX (m) |
| f32 | originZ (m) |

Then, in order:

| type | count | meaning |
|------|-------|---------|
| i16 | nB | year built (0 = unknown) |
| u8  | nB | flags: bit0 approximate year, bit1 landmark (NYC LPC database), bit2 year shared by several footprints on one parcel/record, bit3 estimated height (from floors or a default, not measured), bit4 census-area median year (NSI `med_yr_blt`; always also bit0, so render it distinctly, never as exact) |
| u8  | nB | period index into `index.json` `periods`; 255 = unknown year |
| u8  | nB | floors (>= 1) |
| u8  | nB | use: index into `uses` (residential, commercial, industrial, civic, mixed, other) |
| u8  | nB | yearSrc: index into `index.json` `sources`; 255 = no year |
| u8  | nB | heightSrc: index into `sources` |
| u16 | nB | parts per building |
| u16 | nP | height above base per part, **decimetres** |
| i16 | nP | base: ground elevation per part (m above datum), **decimetres** |
| u16 | nP | rings per part; the first is the outer ring, the others are holes |
| u16 | nR | vertices per ring (no closing vertex) |
| u32 | 1  | byte length L of the vertex stream |
| u8  | L  | vertices, ring after ring: per vertex `zigzag(dx)`, `zigzag(dz)` as LEB128 varints, where d is the difference from the previous vertex of the ring (from 0 for the first), in tile-local **decimetres** |

There are no roof triangles: clients triangulate the top of each part (earcut), because they
re-split rings for wall shading anyway.

Outlines are simplified before encoding (Douglas–Peucker, tolerance 3% of the ring's bbox
diagonal, clamped to 0.35–2 m). This removes the 0.5–2 m stair-steps of LiDAR-traced footprints,
which stripe tall facades when extruded, and about 30% of the vertices.

Sizes for SF, all data files, brotli: SFT4 11.0 MB, SFT5 5.9 MB. Packs alone: SFT4 8.4 MB,
SFT5 3.8 MB.

### SFT6: floating parts and shaped roofs

A tile with a part that does not stand on the ground, or has a shaped roof, has magic `"SFT6"`:
SFT5, then (4-byte aligned after the vertex stream) a sparse list of those parts:

| type | count | content |
|---|---|---|
| u32 | 1 | n: number of listed parts |
| u32 | n | part index in the tile |
| u16 | n | minHeight: the part's bottom above base, **decimetres** (walls start there; clients draw an underside) |
| u16 | n | roofHeight: the share of the part's height taken by its roof, **decimetres** |
| u8  | n | roof shape: 0 flat, 1 dome, 2 onion, 3 pyramid |
| u32 | 1 | m: number of demolished buildings (4-byte aligned) |
| u32 | m | building index in the tile |
| i16 | m | the year it was demolished |

A shaped roof rises from the outer ring at `height - roofHeight` to a point over the ring's
centroid at `height`: a quarter circle (dome; OSM `dome`, `round`), a bulging curve (`onion`) or
straight (`pyramidal`, `cone`). Parts with holes are flat. Unlisted parts have minHeight 0 and a
flat roof. A tile with no listed part and no demolished building is written as SFT5.

Demolished buildings (NYC: Building Footprints Historic, demolitions since 1996) are drawn from
their year built (or from the start, if unknown) until the year they came down, then sink away.
They are not in `yearHist`; `index.json` `demolished` is `{ count, pairs: [[built (0 = unknown),
demolished, n], …] }` so clients can count what stands in any year. In the browser the year is
packed into the storage word `floors + 256*use + 2048*(year - 1600)`.

These come from OpenStreetMap building parts (Overture `building_part`, ODbL): where they cover
≥ 60% of a footprint they replace it, otherwise the parts that stand out (shaped roofs, parts
taller than the footprint's height) are added to it. Other pitched roofs (gabled, hipped, …)
become a flat top halfway up the roof. See `crates/pipeline/src/parts.rs`.

### Landmark models

`index.json` `models` lists hand-built models drawn as part of a building (`landmarks/README.md`):
`{ id, name, file: "models/<id>.glb", gid, x, z, base, rotation, licence, publishable }`. `x`, `z` are
the model's origin in the city frame, `base` the building's ground elevation. Clients draw the
model's triangles with the building's id (`uv = (gid, base)`), so it is coloured and filtered with it.

### Older tiles: SFT3 / SFT4 (still read by `tilefmt::decode` and the worker)

The header is the same except u32 nTI (roof triangle indices) where SFT5 has gid0. Arrays:
- u32 gid[nB]
- i16 year
- u8 flags, period, floors, use
- u32 partStart[nB+1]
- f32 height[nP], f32 base[nP]
- u32 ringStart[nP+1]
- u32 vertStart[nR+1]
- u8 hole[nR]
- i16 xz[2·nV] (absolute)
- u32 triStart[nP+1]
- u16 tri[nTI] (part-local)
- SFT4 only: u8 yearSrc[nB], u8 heightSrc[nB]

SFT3 has no yearSrc or heightSrc.

## index.json

`format`, `city`, `name`, `attribution` (joined from the sources used), `licence` (summary),
`publishable` (true only if every source used is publishable), `origin`, `tileSize`, `regionTiles`, `count`,
`groundDatum`, `bounds` (`min`/`max` [x, z] metres, `lonLat` [[w,s],[e,n]]),
`periods` [{name, from, to, color}] (the map's Classic colours; other colour schemes in
`web/schemes.js` replace them), `unknownPeriod` (255), `unknownColor`, `uses`, `flags`,
`sources` [{id, name, url, licence, attribution, publishable}] (indexed by tile `yearSrc` /
`heightSrc` and attrs columns; `noSource` = 255), `attrsColumns`, `yearHist` {year: buildings}
over final (incl. estimated) years. `version` (only in a static site, see `pipeline site`): a
hash of the city's files, used as the `?v=` of its data URLs,

- `regions` [{id, bbox [minX, minZ, maxX, maxZ], gid0, nB, attrs, packs [{file, size}]}] — a
  region is `regionTiles`² tiles; its gids are contiguous (`gid0 .. gid0+nB`), its packs hold
  only its tiles, its attrs file only its buildings. Load regions by camera view.
- `tiles` [{id "tx_tz", region (index), file, offset, length, origin [x, z], bbox
  [minX, minZ, maxX, maxZ], maxH (max base+height), nB, gid0}] — fetch `file` with an HTTP range
  `offset..offset+length` or load the whole pack.

## attrs/<region>.json

JSON array; row `gid - region.gid0` is
`[address, use description, units, yearSource, heightSource, footprintSource, extra?]`
("" / 0 when unknown; source indices into `index.json` `sources`, 255 = none). `extra` is
present only for some buildings: an object, e.g. NYC `{"ll84": {reportYear, yearBuilt,
siteEUI_kBtu_ft2, energyStar, ghg_tCO2e, use, gfa_ft2}}`.

## Provenance

Every value is chosen per field from per-source candidates by a per-city priority list
(`crates/pipeline/src/city.rs`): the first listed source with a valid value wins; candidates from
unlisted sources are cross-checks only (e.g. NYC LL84 `year_built`). Year candidates are
cleaned per source (placeholder spikes skipped, rounding spikes flagged approximate). Missing
years fall back to: median of nearby dated buildings (`neighbour_estimate`, approximate), then
the NSI census-area median (flag bit4). Missing heights fall back to floors × 3.2 m (heightSrc =
the floors' source, flag bit3), then a type default (`model_default`, flag bit3). The pipeline
log reports the per-field source mix and cross-source conflicts (years > 5 apart; heights >
max(3 m, 25%) apart).

## Licensing

Each source has a `licence` and `publishable` flag. Sources whose licence is unstated (several
Bay Area county/city layers) are `publishable: false` — such outputs are for local use only;
check `index.json` `publishable` before publishing. The `bay` output contains Overture Maps
buildings (ODbL, incl. OpenStreetMap): tiles + attrs are a derived database, so if published as a
database (not just rendered), ODbL share-alike and attribution apply.

## Ground (`pipeline <city> ground`)

All in the same city frame as the buildings (x east, z south, metres from `origin`).

### terrain.json + terrain/t_<ti>_<tj>.bin

USGS 3DEP (1/3 arc-second, public domain) resampled to a regular grid; heights are NAVD88
metres, the same datum as building `base`. Where 3DEP has topobathy, values below 0 are water
depths (SF Bay, ocean): clip or draw the water layer over them.

- `cell` (m), `nx`, `nz`; cell (i, j) has its centre at `x = x0 + i·cell`, `z = z0 + j·cell`
  (row j = 0 is the northern edge; z increases southwards).
- Tile `t_<ti>_<tj>.bin` covers cells `i0 .. i0+nx`, `j0 .. j0+nz` (see `tiles[]`), stored
  row-major (`nz` rows of `nx` values) as Uint16 `v`: `h = offset + v · scale`
  (`scale` = 0.1 m), `v = nodata` (65535) = no data.
  - With `"encoding": "delta-shuffle"`: each row is first replaced by differences from the
    cell to its west (u16, wrapping; the first cell of a row is kept as it is). The file then
    holds all the low bytes, followed by all the high bytes. It is about 28% smaller compressed.
  - Without `encoding`: plain Uint16 LE. Tiles are `tileCells` cells square plus a
  1-cell overlap on the east and south edges (`overlap` = 1), so adjacent meshes share an edge.
  Tiles with no data at all are omitted.
- `min` / `max` per tile and overall, for culling and colour ramps.

### land.bin, water.bin, parks.bin

Overture Maps base theme (from OpenStreetMap, ODbL): `land` (subtype land: coastline-derived
land masses and islands), `water` (all water polygons except pools/fountains), `parks`
(land_use park / golf, recreation grounds, nature reserves, cemeteries, gardens). Clipped to
the city bbox, simplified (`ground_simplify_m`: 2 m, 10 m for bay), triangulated with earcut.

| type | count | meaning |
|------|-------|---------|
| u8[4] | 1 | magic `"SFL1"` |
| u32 | 1 | nV vertices |
| u32 | 1 | nI triangle indices |
| f32 | 2·nV | x, z (metres, city frame) |
| u32 | nI | triangle vertex indices (winding as earcut returns; render double-sided) |

Draw at y ≈ terrain height (or flat at 0 without terrain): land under water under parks.

### Building bases

`tiles` uses the source's ground elevation where it has one (SF LiDAR `gnd_min_m`, NYC, Boston,
Cambridge, Solano), otherwise the lowest DEM sample under the footprint, so buildings sit on
(or slightly into) the terrain mesh.

## Serving (`pipeline <city> compress`)

- **Compressed copies:** `compress` writes `<file>.br` (brotli 11) and `<file>.gz` (gzip 9) next to every `.bin` and `.json`. The API server (`api` crate) sends them as they are.
- **Brotli vs gzip:** browsers only accept brotli over HTTPS, so a plain-HTTP LAN client gets the gzip copy. Re-run `compress` after any step that rewrites outputs; files that are already up to date are skipped.
- **Caching:** the map requests data with the build version (`?v=`: `index.json` `version` when present, else its Last-Modified). The server marks those responses `Cache-Control: public, max-age=31536000, immutable`, so a city is only downloaded again after a rebuild. `index.json` itself is always revalidated.
- **Static site:** `pipeline site` carries `.bin` files only as `<file>.bin.gz` (static hosts send binaries uncompressed and can't be told to send `Content-Encoding`). The browser unpacks them with `DecompressionStream` (`web/dataurl.js`). See `PUBLISHING.md`.
